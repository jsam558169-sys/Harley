# Harley's Inventory and Sales System — Functional Core

This is the **functionality-first** build: real Firebase-backed logic with
plain, unstyled screens (default Material widgets, no theming). UI polish
comes later, once everything below actually works end-to-end.

## 1. Prerequisites

- Flutter SDK installed (`flutter --version` should work)
- A Google account for Firebase
- Node.js (needed by the FlutterFire CLI)

## 2. Turn this into a runnable Flutter project

I gave you `lib/` and `pubspec.yaml` only — not the platform folders
(`android/`, `ios/`, `web/`), since those need to be generated by the Flutter
tool on your machine. From this project's root folder:

```bash
flutter create .
flutter pub get
```

This adds the missing platform folders without touching your `lib/` code.

## 3. Connect Firebase

```bash
dart pub global activate flutterfire_cli
firebase login          # if you haven't already (needs firebase-tools: npm i -g firebase-tools)
flutterfire configure
```

- Create/select a Firebase project when prompted.
- Choose the platforms you want to build for (Android/iOS/Web — pick at least one).
- This **overwrites** `lib/firebase_options.dart` with your real project's values.

Then in the [Firebase Console](https://console.firebase.google.com):

- **Authentication** → Sign-in method → enable **Email/Password**
- **Firestore Database** → Create database → start in **test mode** for now
  (we'll lock it down with security rules later, once functionality is confirmed)

## 4. Bootstrap your first Owner account

The app can only create new users *from inside* the app, once someone is
already logged in as Owner (see `RegisterUserScreen`). For the very first
account, you have to create it manually:

1. Firebase Console → Authentication → Add user → enter an email + password.
2. Copy the generated **User UID**.
3. Firebase Console → Firestore Database → start collection `users` →
   document ID = that UID → add fields:
   - `userEmail` (string) — same email you used
   - `role` (string) — `owner`
   - `displayName` (string) — whatever you like

Now log into the app with that email/password and you'll land on the Owner
menu, which includes "Register New User" for creating employee accounts
normally from then on.

## 5. Run it

```bash
flutter run
```

## What's implemented (functionality, not UI)

Mapped to your Chapter 2 objectives:

- ✅ Digital sales recording (POS screen → `SalesTransaction`)
- ✅ Automatic ingredient deduction per recipe when a sale completes
  (`SalesService.completeSale`, run inside a Firestore transaction so stock
  can't go negative from a race condition between two simultaneous sales)
- ✅ Ingredient, finished-product, and stock-in/out management
- ✅ Full stock movement audit log, including auto-generated stock-outs from sales
- ✅ Ingredient usage tracking per sale, for consumption reporting
- ✅ Low-stock detection (≤ 5 servings, per your objective) computed from
  recipe + on-hand ingredient quantity
- ✅ Expired-ingredient handling: mark expired → auto-deducted from usable
  stock → auto-recorded as a loss
- ✅ "Replaced order" loss recording (from your Chapter 1 description of
  comped/replaced dishes)
- ✅ Daily / weekly / monthly sales reports + ingredient usage summaries
- ✅ Role-based access via two separate dashboards, per the feasibility study:
  - `AdminDashboard` (Owner): everything, including Products/Recipes
    management, full sales+usage Reports, Losses, and Register New User.
  - `EmployeeDashboard`: Process Sale, Ingredients & Stock (stock-in/out +
    marking expired, but can't add/delete ingredients from the catalog),
    Stock Movement Log, Low Stock Alerts, and an ingredient-usage-only
    version of Reports (no revenue figures).
  - `LoginScreen` routes to the right dashboard automatically based on
    `AppUser.role` after login.

## Known gaps / things I made assumptions about (flag if wrong)

- **Branch selection**: the POS screen hardcodes `"Juan Luna"` as the branch.
  Your doc mentions two branches (Juan Luna and Toril) — I'd add a simple
  dropdown for this next.
- **IDs**: your data dictionary lists `Integer` IDs (e.g. `productId`). I used
  Firestore's native auto-generated document IDs (strings) instead, since
  that's how Firestore is meant to be used and avoids you having to manage
  an ID counter yourself. Let me know if this matters for your paper/defense.
- **salesReport collection**: reports are computed on-demand from
  `salesTransaction` + `ingredientUsage` data rather than being pre-stored,
  since with modest transaction volume that's simpler and always accurate.
  There's a `cacheReport()` method ready if you want to persist snapshots later.
- No Firestore **security rules** yet (test mode = anyone can read/write).
  I'd add role-based rules once the app logic is confirmed working, before
  any real deployment.
- No receipt printing / delivery-app integration (explicitly out of scope
  per your Chapter 2).

## Project structure

```
lib/
  models/       - one file per Firestore collection (data classes only)
  services/     - all Firebase read/write logic + business rules
  screens/      - plain functional UI, wired to the services
    login_screen.dart      - login + owner-only "register new user" form
    admin_dashboard.dart   - Owner/Admin menu (everything)
    employee_dashboard.dart- Employee menu (operational subset)
    ...                    - the rest are shared screens both dashboards link to
  main.dart     - entry point
  firebase_options.dart - PLACEHOLDER, replaced by flutterfire configure
```
